# V3 outbound cooperative pole

Open `Assets/Game/Gameplay/Scenes/V3Gameplay.unity`. Create a Relay room, join from a second process, then start the game on Host. The pole wrapper belongs to the Gameplay bootstrap, outside every level `Generated` hierarchy. Start placement uses `Mountain.V3.Start`; permitted summit IDs and landing areas use `MountainConfigV3`. Do not run a level generator to install this feature.

Approach either end and press E. The first participant becomes pivot; the second receives the remaining grip. Both participants are required for rotation and the private transparent support under the **orbital** participant, as specified by the integrated planning document.

- Orbit: A/D rotates horizontally; W/S adjusts elevation within the configured pitch limit.
- Pivot: WASD carries both endpoints at 2 m/s while both have real support on the same summit. Once the orbit leaves the summit the pivot remains fixed.
- Stop on a different, safe summit. After the landing dwell, the orbital player presses E to exchange roles.
- Esc releases the pair; F4 toggles pole diagnostics. F3 remains the foundation diagnostics key.

Controls, spherical yaw/pitch movement, support dimensions, landing thresholds, carry speed and pole dimensions are implementation hypotheses, not finalized planning values. The 32 m pole has an effective endpoint-to-pivot radius of 32 m. V3 uses authored rock landing terraces, a directional Final approach cut, and real rock canyon cuts outside the endpoint landing rims to tune spacing and prevent walking shortcuts. Terrain candidates require collider and continuous-pose validation; a connected graph alone does not establish a completed playable route.

The server owns an atomic pole snapshot and validates sender, phase, revision, grip range, real terrain support and collision sweeps. Attached characters suspend normal movement and OwnerNetworkTransform updates; the pole snapshot drives both endpoint poses. On release the owner restores its normal transform stream. Ordinary unattached characters retain their existing controller and ownership. Cancelling or disconnecting releases both grips. Collision failures respawn the failed participant through existing per-player checkpoints; the partner is released. The planning document does not mandate shared mountain respawn, so that behavior remains a documented hypothesis. No intermediate checkpoint is added.

`Tools > Twin Edge > Gameplay > Validate Cooperative Pole` loads saved assets and performs geometry and real collider queries without regenerating terrain. `Install Cooperative Pole` creates missing wrapper assets and installs only Gameplay references; it prompts to save modified scenes in interactive Editor use. Build with `TwinEdge.Gameplay.Editor.GameplayFoundationSetup.BuildPlayer`.

For opt-in development automation, launch two builds with `-poleSmoke host` / `-poleSmoke client` and `-poleEvidence <fresh absolute directory under ignored Docs/Development/Gameplay/V1/>`. This uses real Relay with station positioning for setup. It does not prove crossing a gap or manual control feel. Optional local evidence and implementation notes live under ignored `Docs/Development/Gameplay/V1/`; fresh clones do not need them.


V3 terrain validation: open V3Gameplay plus LevelBlockoutV3 additively, then use `Tools > Twin Edge > V3 Mountain > Analyze Pole Reachability`. `Level Visualization > V3 Mountain / Pole Reachability` displays actual supported grid samples and isolated swept arc candidates. Yellow graph routes are mathematical/collider candidates, not successful gameplay. Red pairs may include search limitations; the tool samples at 1 m on tuned terraces and 2 m elsewhere with bounded candidate counts. Ordinary interactive Mountain regeneration schedules analysis automatically; re-run manually after Undo/Redo or other collider edits. `MountainPoleContinuousPlan.Run` additionally checks connected endpoint poses, same-summit carrying, rigid rotation and exchange candidates. Optional reports go under ignored `Docs/Development/Gameplay/V1/MountainPole/` and are not fresh-clone dependencies.

For opt-in development Relay input replay, run a development build in two processes with `-mountainPoleRun host` / `client`, `-mountainPolePlan <absolute ContinuousPlan.json path>` and `-mountainPoleEvidence <fresh absolute ignored evidence directory>`. The plan must be generated and validated against the same saved terrain/pole configuration. Initial grip station placement is setup only; all subsequent traversal uses production steering, landing dwell and exchange RPCs. A pass requires both peer results; earlier smoke results do not certify this route. Human play and failure/recovery regression remain separate acceptance checks.


After an actual airborne rotation, a downward capsule contact may settle on a validated walkable summit: the server retains the previous collision-free authoritative sphere pose only if five-point landing support already passes there, every capsule sweep contact has normal Y>=.85, and the rod remains clear. This is a collision stop, not a terrain snap or radius adjustment. A stationary blocked contact can satisfy the usual landing dwell; exchange still requires a different summit and the orbital participant. Wall/rod/unsafe contacts retain failure and respawn. Initial grounded downward misuse retains failure; an attached pair must actually leave support before this landing capture is enabled. Role exchange and release reset that server-only flight state. Late Relay steering therefore cannot drive a valid arrival through the floor before the client observes the landing.
